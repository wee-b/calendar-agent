# 工具调用评估与控制

对话主图为每轮请求绑定一个 `ToolExecutor`，普通响应和 SSE 共用。Chat、规划前置日程查询、Planner 实际工具查询和 Executor 都经过统一边界；只读重试位于该边界内。模型轮数、并发数与实际工具尝试次数分别限制。

## 部署与配置

已有数据库先执行 `sql/migrations/20261026_tool_call.sql`，再发布 Python 服务。脚本只添加 `yl_tool_call`，可重复执行；新建数据库的 `sql/tables.sql` 已包含相同结构。应用不会启动时自动迁移，也没有对业务数据库自动执行升级脚本。

可在 `ai-service/.env` 或进程环境变量覆盖，修改后重启：

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `MCP_CALL_TIMEOUT_MS` | 5000 | 未提供工具专属超时时的单次上限，毫秒 |
| `MCP_READ_RETRY_ATTEMPTS` | 2 | 只读工具最大尝试次数，包含首次，即默认最多重试一次 |
| `MCP_READ_RETRY_DELAY_MS` | 250 | 只读重试等待时间，毫秒 |
| `MCP_TURN_MAX_CALLS` | 12 | 一次用户输入允许的实际工具尝试总数，包含重试、跨节点共享 |
| `MCP_TURN_BUDGET_MS` | 60000 | 一次用户输入所有尝试与重试等待的累计耗时预算，毫秒 |

Executor 优先使用已校验工具目录中的 `timeoutMs`，其他入口使用统一缺省值；执行时再取与剩余预算的较小值。该有效超时同时传给 HTTP 客户端及外层 `asyncio.timeout`，避免批量写入声明30秒却被 HTTP 客户端的默认5秒提前中断。目录查询仍使用 `JAVA_REQUEST_TIMEOUT`，单独受整轮请求超时保护，不计入业务工具次数。

预算按各次尝试耗时之和结算，并行时不等于整轮墙钟时间。并发请求在第一个 `await` 前原子预留其超时额度，完成后退还未用部分；不足时保守拒绝准入，不超卖预算。等待重试也预留并结算，失败尝试同样扣费。预算不包含模型等待、工具目录查询或审计数据库写入；外层 `CHAT_STREAM_TIMEOUT_SECONDS` 继续约束完整请求。

达到次数上限返回 `42902`，耗时预算不足返回 `42903`。已知模型同批调用数量超过剩余额度时，在执行该批前拒绝；重试仍逐次检查。预算错误终止后续执行，不交给模型重新申请工具来绕过限制。

## 记录与统计口径

`yl_tool_call` 每行代表一次已准入的实际尝试，字段包含用户、会话、轮次、逻辑调用 ID、尝试 ID、Agent、工具名、读写属性、尝试序号、有效超时、终态及耗时。时间按 UTC 保存。不保存 token、提示词、工具参数、原始结果；写操作仅保存去重摘要。

一次逻辑查询超时后重试成功，产生两行，逻辑调用 ID 相同，尝试 ID 不同。缓存/快照复用不产生新的实际尝试；Planner 复用预加载偏好时不再重复计数。规划内部的记忆、文档资料准备和模型 API 沿用各自原有边界，不把任意数据库查询都当成工具。Planner 实际请求本地 `queryPreferences` 时计入工具尝试，不自动重试。

每次尝试向 `app.tool` 输出开始及一个终态事件：`success / timeout / error / cancelled`。业务结果通过校验后才记录成功。整轮 `app.flow` 的 `flow_details.工具调用` 保存明细，`工具调用统计` 保存实际次数、逻辑次数、分类数量和耗时之和；零工具轮次也输出 count=0。重试等待消耗预算，但不属于单次工具执行耗时。

读写操作的传输状态与业务结果分开：`status=timeout` 可以同时有 `outcome=uncertain`。写记录开始时就使用 `running/uncertain`，表示结果尚未确认；成功校验后改为 `success/success`。这样进程异常退出、无法落终态时也留下保守的待核实依据。进行中的写请求也包含在 uncertain 数量内，应结合 running、started_at 和 timeout_ms 判断，不把它直接解释为已失败。

## 查询接口

均要求登录，仅查询当前用户数据，不接受客户端指定用户身份：

- `GET /chat/tool-calls?sessionId=s&limit=30&beforeId=...`：降序游标分页，limit 为1～100。返回轮次、逻辑/尝试 ID、状态、业务结果、超时、耗时与时间，不返回去重摘要或参数。
- `GET /chat/tool-stats?start=2026-10-26T00:00:00%2B08:00&end=2026-10-27T00:00:00%2B08:00&sessionId=s&turnId=...`：默认最近24小时，最多31天，显式时间须携带时区；会话和轮次筛选均可省略。

统计结果的 `count` 包括进行中的尝试，`running` 单列进行中次数；`completed` 提供已结束尝试总数、成功/超时/失败/取消数、成功率、平均耗时及 P95，`tools` 按工具提供相同指标。成功率分母为所有已结束尝试，包括失败、超时和取消。没有已结束样本时，成功率、平均及 P95 为 null。

P95 在 MySQL 8 窗口函数中按 nearest-rank 计算：排序后取第 `ceil(n*0.95)` 项；总体 P95 使用所有样本重新计算，不平均各工具的 P95。`per_turn` 返回有调用轮次的数量、每轮平均/最大次数及逻辑调用总数。传入 `turnId` 可查看指定轮次的实际次数；无调用轮次的零值在整轮日志中，不计入数据库的每轮平均值。

## 写操作保护与核实边界

写入前先独立提交审计记录，然后设置本轮写标记，再发出请求；写记录失败时不会发送业务写请求。所有写工具仅尝试一次。写超时、取消、连接中断、返回结果无效或写后会话提交失败时，保留原有 `processing=1`，阻止同一会话再次确认、撤回或删除后重放写入；用户收到 `40903` 待核实提示（主动断连时通过后续明细查看）。

写去重摘要包含服务端用户、会话、认领版本、工具名和规范化参数，同一认领内有唯一约束。规划同步使用草稿 ID 替代认领版本作为稳定操作范围，避免同一草稿在会话意外解锁后重放；未来新任务的合法相同操作不会被永久封禁。

终态提交有5秒的有界保护，取消时仍尝试保存。若成功操作的终态无法保存，停止链路；写操作继续保留会话认领。未回收的 running 写记录应作为待核实记录处理，不能因时间过去而自动改为失败或释放认领。已成功的多步写入不会回滚为“全部失败”。

核实流程仍为人工检查日历、对应会话的 pending 任务/草稿及调用明细，然后由维护者修复草稿和会话状态。此版本没有新增未经核实即可解锁的公开接口。审计去重摘要不是 Java 业务幂等键，不能证明跨会话相同需求只执行一次；自动核实与跨会话幂等需要 Java 事务内持久化操作 ID 和结果查询接口，尚未实现。

## 验证

从 `ai-service` 运行：

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_tool_execution tests.test_tool_call_api -q
```

MySQL 集成测试 `tests.test_tool_call_persistence` 沿用 `CHAT_TEST_MYSQL_URL`，只创建并清理随机测试库，不清空指定库。覆盖迁移重复执行、真实 P95、分页与用户隔离、唯一操作并发争抢、终态只更新一次，以及真实会话认领下写超时后再次确认被阻断。
